01三条必须先讲清的红线

红线一 · 约束冲突（最重要） 作业题干要求端侧推理、无云端兜底。视频生成 API 的全部算力都在厂商机房，属于典型的云端兜底。若把它写进正式方案，等于自己推翻了 Part1 的模型选型与评估结论。正确做法：单独开一个「演示增强」目录，明确标注不进正文，答辩时作为「如果放开约束，架构怎么扩展」的加分回答。
红线二 · 接口形态完全不同（异步，不是同步） 生产级视频 API 几乎全是 提交任务 → 拿 task_id → 轮询 的两段式，单片段通常 1~5 分钟。而 Dify 云端工作流整体超时默认约 200 秒、HTTP 节点建议 30 秒，直接把视频 API 塞进现有那个 HTTP 节点会必然超时。必须加一层「异步转同步」的适配器，或者改成提交后交给队列状态机。
红线三 · 需要资质与钱 国内主流平台基本都要实名认证、充值，按秒计费约 0.25~0.9 元/秒；免费额度多半是网页端积分，不等于 API 免费额度。作业演示建议只用免费 API 或明确的降级模式，避免现场翻车。
好消息 这些约束带来的「异步任务 / 状态机 / 失败重试 / 超时后保留 task_id / 显式降级」，恰好就是文档3《多任务并发与不丢稿》里已经设计好的东西。接视频 API 不需要改架构，只需要换一个驱动 —— 这点在答辩里非常值钱。

02标准接入形态：三段式异步链路

下图是各家视频 API 的通用形态（硅基流动 /video/submit + /video/status、阿里百炼 X-DashScope-Async、可灵、即梦、MiniMax 都是这个套路）。

一个容易踩的坑 本地轮询超时 不等于任务失败。必须把 requestId 持久化下来让别的 worker 续查；绝对不要重新提交一次，否则会生成两段视频、重复扣费。这正是文档3「不丢稿」要解决的问题。

04三条可选路线（按推荐度排序）

A · 保持现状（推荐交作业）

用本目录的适配器接免费/低价视频 API，产出真 MP4。必须单独标注不进正文，且要准备回答「这算不算云端兜底」。

实测结论：812 Insufficient corporate funds, please top up Key 本身完全有效。但模型 API 只认「企业级-共享」Key 绑定的团队余额；个人钱包里的 RH 币 / 会员权益不会自动给这把 Key 用。所以「我账户里有费用」和「这把 Key 能扣到钱」是两回事。
已排除的其它可能：不是参数错、不是端点错、不是站点错 —— 三个不同模型端点 + .ai/.cn 双域名，只要参数合法就一律返回 812；参数不合法时反倒先返回 1007，说明资金检查在参数校验之后。

两条解法

A · 给团队余额充值（最省事）
在「任务与账单 → 钱包 / 充值」确认充值落在团队 / 企业余额（不是个人钱包）。充值后这把 Key 立刻可用，不用改代码、不用换 Key。密钥页右上角有「API Key 调用权益对比」可核对。
B · 换消费级-会员 Key 走工作流 API（已验证成功 ✓）
若你的钱在个人钱包 / RH 币里，可新建一把「消费级-会员」Key，改走 /task/openapi/* 工作流通道。代价：需要一个已保存且手动跑过一次的视频工作流 ID（工作流页面 URL 里那串数字）。适配器已支持 --provider runninghub_workflow --workflow-id ...。本轮已实测成功并产出 MP4，且公开工作流 ID 可直接用，无需用户手动跑一次。

# 会员 Key 走工作流 API（本轮实际成功的那条命令）
export RUNNINGHUB_API_KEY=你的会员Key
python3 video_api_adapter.py --provider runninghub_workflow \
  --workflow-id 1970121357323366402 \
  --node-info '[{"nodeId":"5","fieldName":"text","fieldValue":"雨后天台，穿黄雨衣的柯基叼着发光棉花糖..."}]' \

# 任务已成功但没拿到文件时：复用 taskId 续查，不重新提交、不重复扣费
python3 video_api_adapter.py --provider runninghub_workflow \
  --task-id 2117981722906030081 --save demo_output/corgi_clip.mp4
参数坑（实测） 不同模型端点的 duration 枚举不一样：wan-3.0-prime 允许 4，但 rhart-video-v3.1-fast 只允许 8，写 4 会返回 1007 ... allowed values: 8。适配器已把这类业务错误翻成人话，直接看 reason 即可。
另外两个实测工程坑：① /task/openapi/status 的 data 是纯字符串 "RUNNING"/"SUCCESS"，不是对象；② /task/openapi/outputs 的 data 是数组，取 fileUrl 要遍历列表。适配器已两处都修好。
安全提醒 两把 32 位 Key 都已经出现在对话里。等演示跑通、余额确认后，建议到密钥页重置 / 删除并重新生成一把，只放在本地环境变量里，不要写进任何提交到 GitHub 的文件。本仓库所有代码都只从 RUNNINGHUB_API_KEY 环境变量读取，未硬编码密钥。
