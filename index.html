这套作业到底在问什么（30 秒版）

假设有一台不能联网的 AI 作图主机，上面装了个叫 AI Studio 的画布软件。你要当这个产品的 PM，回答两件事：① 装什么模型、怎么评估它；② 软件怎么做、多任务怎么不崩。老师最后要的是「三个文档 + 一个 demo」，并且两个场景都要做完整的一套，所以这里是 6 份文档 + 2 个 Demo；另外补了一层 Dify 工作流 + API 接入，用来兑现题干里「接入 API」那半句——Demo 因此从「能点的界面」升级成「界面 + 能跑的编排链路」。整套方案只有一条红线：全部推理在本地，无云端兜底——所有决策都从这条线推出来。

课前 3 分钟 · 先给自己看一页纸如果不熟悉技术细节，先打开 课堂速记（答辩提纲）：6 个可能被问到的问题都写成了能直接说出口的大白话，还标了演示时点哪几下。这份是给自己准备的，不是必交内容；随压缩包一起交也没关系，相当于一份答辩提纲。

02两套方案为什么必须分开做

维度电商素材工作流短剧自动化工作流
产物 / 单任务时长静态图，5–8 秒视频镜头，1–10 分钟
主力模型Z-Image-Turbo GGUF Q5 + Qwen-Image fp8Qwen3-4B + Z-Image + Wan2.2 TI2V-5B / LTX-Video FP8
一致性对象商品形状 / LOGO / 配色人物身份 / 服装 / 跨镜头
一致性手段IP-Adapter + 商品锚图 + 蒙版re-anchor + 角色 LoRA + OpenPose + 关键帧先行
算力瓶颈显存峰值、模型切换显存带宽、64GB 内存、NVMe 帧缓存
并发核心任务级队列、前台编辑插队镜头 + 帧段双层状态机、分段 checkpoint
失败代价重跑一张重跑几分钟 → 必须按帧段续跑
最坏情况交付降分辨率仍可出图降级为分镜故事板，视频任务转待办
质量 vs 速度都保速度，但理由不同都保速度，靠预演档 / 终稿档分层
一句话记住差异电商的难点是「像不像、快不快」，短剧的难点是「会不会中途崩、崩了能不能接着跑」。模型选型、模块划分、并发策略因此完全不同，合并成一份会两边都讲不透。

03共同前提：三条硬约束 + 硬件假设

全部推理在本地
任何方案里都不出现「调云端 API 兜底」。性能不足只能降级、排队、取消、拒绝。
目标用户是内容创作者
要批量出片、能直接交货、素材保密。所以商用许可与吞吐比跑分更重要。
产品是三层协作
本地大模型 + 接入 API + 创作应用，靠账号 / 授权 / 算力调度协同。加分项文档正是「算力调度」的展开。
项目假设规格为什么这样假设
GPU单卡 24GB 显存（RTX 4090 档；32GB 为可选高配）2026 年本地创作主机的主流档位；24GB 是 FP8 大模型的实际门槛
系统内存64GB DDR5视频工作流的 T5-XXL 文本编码器常需 offload 到内存，10–20GB
存储2TB Gen4 NVMe（≥5000 MB/s）模型加载、帧缓存、草稿落盘都吃磁盘；首图慢主要是加载而非计算
网络完全离线，无外网、无云端兜底题目硬约束；所有失败只能在本地消化
使用方式单机单卡，本地账号区分使用者对应题干的「账号 / 授权 / 算力调度」平台能力
显存预算峰值 ≤ 20GB，预留 4GB 给画布、VAE 解码与激活留余量是避免 OOM 的第一道工程约束
需要你确认的第一件事上面的硬件规格是我按 2026 年主流端侧创作主机设的假设。如果老师课上给过具体机型（比如显存是 16GB 或 32GB），告诉我，我把两套文档里的显存账和模型档位一起改。

07关于 Dify 工作流与 API 接入（回应「这才算 demo 吧」）

题目中 demo 要求的是可交互原型 / 线框 + 交互说明，所以两个 HTML 工作台保留；但题干「本地大模型 + 接入 API + 创作应用」这句，纯界面原型证明不了。于是补了一层可导入 Dify 的工作流 + 可运行的本地编排服务，把「点下去之后数据怎么走」也做成实物。

画布（两个 HTML Demo）→POST /v1/workflows/run→Dify 工作流：LLM → 代码校验 → HTTP→本机出图 API / ComfyUI→data.outputs 回包

最小演示：双击 03_Dify工作流与API接入/启动本地服务.command → 打开 Demo 勾选「接入本地工作流」→ 电商点「批量生成」或短剧点「解析为结构化分镜」→ 日志出现工作流回包；关掉服务再点一次，会自动回退、界面不崩。

新增了什么
两份可导入 DSL（yml）、一个零依赖 Python 编排服务、一份完整接入说明 HTML、一个双击启动脚本。
为什么不算超纲
老师要的仍是「三文档 + 一 Demo × 两套」；这一层定位成 Demo 的可运行后端，没有改动文档结构。
红线守住了吗
守住了：Dify 必须自部署、LLM 指向本地 Ollama / vLLM、所有 URL 是回环地址、降级只写降分辨率 / 减候选 / 排队 / 取消。
诚实边界
默认离线模式下编排服务不加载模型权重、不产出真实图像，只验证链路；真机切 --engine local 接 ComfyUI /prompt 即可，上层零改动。联网出图是独立的 DEV ONLY 开发通道，不进作业正文。

08关于「没有显卡，能不能真的跑起来」（回应落地追问）

一句话作业方案里的 24GB 显卡是显式硬件假设；你这台 MacBook Air M5 / 16GB 统一内存 / 无独显，照样能把整条编排链路跑起来（本来不需要显卡），也能通过开发演示通道看到真实图片。四条路线严格隔离，云端引擎是 DEV ONLY，不进作业正文。
路线要网 / 要显卡能得到什么
A · 链路演示（默认）都不要任务拆分、队列、中断、失败恢复、自动存稿，全部真能点；不出像素
B · 联网真出图要网，不要显卡真实 JPEG 落盘并显示在画布（已实测：512×512 / 7–9 秒 / 零注册；匿名 45 秒 1 张）
C · 纯离线真出图都不要Draw Things / mflux / stable-diffusion.cpp 走 Apple Metal，慢但断网可出图
D · 生产落地不要网，要 24GB 显卡--engine local 接本机 ComfyUI，上层接口零改动

最省事：双击 04_可落地运行/一键联网演示.command → 浏览器自动打开页面 → 在 Demo 里勾「接入本地 Dify 工作流」→ 点「批量生成」，约 10 秒出真图。关掉终端再双击 03_Dify工作流与API接入/启动本地服务.command 即切回纯离线。

必须分清的两件事云端是「显式切换的主引擎」，不是「本地失败后的兜底」。作业正文（01 / 02 / 03 目录）里 cloud_fallback 恒为 false，没有任何自动上云分支；04 目录是给没有显卡的机器做开发验证用的，不写进文档①~④。文档 ⑤ 第 03 节还做了 24GB → 16GB 的模型账敏感性重算，说明硬件变了哪些档位要砍。

10视频 API 接入可行性（演示增强，不进作业正文）

红线提示题干要求「全部推理在本地、无云端兜底」。视频生成 API 的算力全在厂商机房，属于典型云端兜底，因此本目录只作为对照实验 / 答辩扩展问答，不改变文档5 里「16GB 机器显式降级为分镜故事板 + 关键帧、视频任务转待办」的正式结论，也不计入 3 文档 + 1 Demo 的提交清单。

结论：技术上能接，且生产级视频 API 的「提交任务 → 轮询 → 取 video_url」异步形态，与文档3 已实现的队列状态机、失败恢复、不丢稿完全同构 —— 只需在驱动层加一个适配器，编排层不用重写。三处必须注意：异步任务 1~5 分钟会撞上 Dify HTTP 节点 / 工作流超时、国内平台需实名充值（约 0.25~0.9 元/秒）、免费网页积分不等于免费 API 额度。
