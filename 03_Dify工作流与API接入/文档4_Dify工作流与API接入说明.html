题目里 demo 的原文是「用熟悉的 AI 工具搭可交互原型，或给出关键页面线框 + 交互说明」——考的是前端界面，所以两个 HTML 工作台不能少。但题干还有一句「产品 = 本地大模型 + 接入 API + 创作应用」，纯界面原型证明不了中间那层。这份补充交付做的就是它：Dify 自部署工作流把一句需求拆成结构化任务，本地编排服务把任务交给本机推理引擎，画布负责让人操作。三者合起来，才是题干说的那台小作坊。

01为什么 Dify 工作流算 Demo 的一部分，而不是第四份文档

题目原文 / 考点原来的 HTML 工作台补上 Dify 之后
「用 AI 工具搭可交互原型」画布、批量参数、队列、中断 / 恢复、自动存稿都能点不变，继续当界面层
「本地大模型 + 接入 API + 创作应用」只在文档里用文字描述过三层关系有可导入 DSL、可调用 API、实测回包，三层真的接起来了
「账号、授权、算力调度协作」文档 ③ 展开了算力调度API 的 user / Bearer Key / 单执行槽 / stop 接口把账号与授权落到接口上
「全部推理在本地，无云端兜底」文档里做了声明DSL 与服务的所有 URL 都是本机回环，回包里带 local_only=true 与 cloud_fallback=false
一句话记住分工HTML 原型回答「长什么样、怎么点」，Dify 工作流回答「点下去之后数据怎么走」。两者是同一个 Demo 的两层，不是两份互相竞争的作业；老师要的「三个文档 + 一个 demo」结构没有被改动。

02一条不能踩的红线：必须全本地

配置能不能用原因
Dify Cloud / api.dify.ai禁止云端 SaaS，编排本身跑在别人机器上
LLM 节点填 OpenAI / Claude / 云端大模型 Key禁止推理出本机，直接违反题设
HTTP 节点指向公网出图 / 视频 API禁止就是被明令禁止的「云端兜底」
RunningHub / 云端 ComfyUI 平台 API禁止云端 GPU + 云端推理，正是题设明令禁止的兜底形态
Dify 社区版 Docker 自部署可以与创作应用跑在同一台端侧主机
LLM 节点指向 Ollama / vLLM / LocalAI / Xinference可以OpenAI 兼容接口，权重在本机
HTTP 节点指向 127.0.0.1 / host.docker.internal可以本机回环，不出网
最容易一句话穿帮的地方千万别写「模型跑不动时切到云端 API」。本套 DSL 的降级只写降分辨率、减候选、排队、取消；代码节点里还把 fallback 字段硬改成本地降级顺序，连提示词都禁止模型写出云端兜底。
RunningHub 要不要接？不要 —— 但要写进「考虑过并排除」RunningHub 是海马云旗下的云端 ComfyUI 平台：浏览器里拖节点、调用云端 GPU、按量计费、对外提供工作流 API。它解决的是「本机没有显卡、不想配环境」的痛点，而这道题的前提恰恰是全部推理在本地完成，无云端兜底——接上去等于把最核心的约束直接推翻，写一句「调用 RunningHub API 出图」整份方案就作废。正确做法是把它当成对照方案：主动说明「考虑过云端 ComfyUI，因推理外移而排除，本机改用 ComfyUI 加载本地权重」，老师追问时反而能证明你读懂了题设。

唯一不越界的用法：只拿它练手设计工作流——在云端把 ComfyUI 节点连好、导出 workflow_api.json，再把这份 JSON 放回本机 ComfyUI 跑，推理仍在本机。它属于学习工具，既不写进正式方案，也不出现在任何降级链路里。
和课程里学的 Dify 有什么不同课上多半用的是 Dify Cloud 版，随手填个大模型 Key 就能跑。这道作业里要额外说一句：换成自部署社区版 + 本地模型供应商。这一点主动写出来，比闷头贴截图更能体现「端侧意识」。

04两份 DSL 逐节点说明

套装 A · 电商素材工作流（5 节点 / 4 连线）

#节点类型输入 → 输出解决的问题
1开始 · 批量参数start商品名 / 风格 / 尺寸 / SKU 数 / 候选数 → 6 个输入变量把画布上的表单变成 API 的 inputs 字段
2本地 LLM · 需求拆解llm变量 → 严格 JSON（plan_id / engine / tasks[]）把一句话拆成可执行的批量任务，不画像素
3代码 · 结构化校验codeLLM 文本 → plan_json / request_json / task_count / summary去 Markdown 围栏、补字段、裁剪数量、复核无云端约束
4HTTP · 提交本地出图http-requestrequest_json → POST host.docker.internal:8765/api/ecom/generate把任务清单交给本机 ComfyUI 封装层
5结束 · 回传画布endplan / generate_result / summary / task_countdata.outputs 即画布渲染队列的数据源

套装 B · 短剧自动化工作流（5 节点 / 4 连线）

#节点类型输入 → 输出解决的问题
1开始 · 剧本与边界start剧本 / 分镜数 / 档位 / re-anchor → 4 个输入变量把端侧边界当参数暴露给创作者
2本地 LLM · 拆分镜llm剧本 → JSON（characters / shots[]）结构化分镜：景别、动作、时长、提示词、机位
3代码 · 边界裁剪codeLLM 文本 → plan_json / request_json / shot_count强制 dur ≤ 5s、identity_ref 回原始锚图、图先行只排关键帧
4HTTP · 提交关键帧http-requestrequest_json → POST /api/drama/generate审片通过前不启动昂贵的 I2V
5结束 · 回传审片台endplan / generate_result / summary / shot_count镜头卡片墙直接消费这份结构化结果
两份不是复制粘贴电商的代码节点守的是多 SKU 一致性（锚图锁定、候选数裁剪）；短剧守的是端侧算力边界（时长、身份漂移、图先行）。这正是文档 ① 和文档 ③ 里两套方案差异在编排层的延续。

05结构化输出：为什么用「提示词约束 + 代码校验」

Dify 支持在 LLM 节点开启结构化输出并写 JSON Schema，但在这道题里直接依赖它是有风险的：

  • 端侧小模型不一定原生支持。官方文档明确：模型不支持时 Dify 会退化成「把 Schema 塞进提示词」，回复仍可能不合规，节点运行会失败。
  • 版本稳定性。社区已知 1.14.0 出现过 structured_output_enabled 静默失效的问题（issue #35789），把整条链路押在单一开关上不划算。
  • 无云端兜底。别的方案解析失败可以换个更强的云端模型重试，这里不行，必须在本机把兜底做实。

所以本方案用三层保证：① 系统提示词把 JSON 结构、字段类型、禁止项写死；② 代码节点去围栏、json.loads、补齐必填字段、裁剪数量；③ 解析失败走本地规则兜底生成一份合法计划，绝不转云端重试。DSL 里没有用原生开关，导入任何版本都能跑。

{
  "type": "object",
  "properties": {
    "plan_id":    {"type": "string"},
    "engine":     {"type": "string", "enum": ["Z-Image-Turbo Q5_K_S", "Qwen-Image fp8"]},
    "anchor_lock":{"type": "boolean"},
    "tasks": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "sku": {"type": "string"}, "style": {"type": "string"},
          "size": {"type": "string"}, "candidates": {"type": "integer"},
          "prompt": {"type": "string"}, "seed": {"type": "integer"}
        },
        "required": ["sku", "style", "size", "candidates", "prompt"]
      }
    }
  },
  "required": ["plan_id", "engine", "anchor_lock", "tasks"]
}
这里藏着一个产品判断把「模型一定会吐合规 JSON」这种假设，换成一个在端侧也成立的工程保证。课堂上讲结构化输出时，能补一句「端侧小模型要配代码校验兜底」，比只会点开关更像是 PM 的回答。

06API 契约（与 Dify 官方形态对齐）

工作流发布后，Dify 官方端点是 POST /v1/workflows/run，请求体为 inputs（变量名必须和开始节点一致）、response_mode: blocking、user（终端用户标识），鉴权用 Authorization: Bearer app-xxx。本地编排服务提供了同形态的接口，所以在没装 Dify 的机器上也能把链路跑通；换成真 Dify 时只改域名和 Key。

字段类型示例 / 说明
inputsobject键名 = 开始节点变量名；电商 6 个、短剧 4 个
inputs.scenestring本地服务用来分派电商 / 短剧；真 Dify 里由不同应用各自承担，可不传
response_modestringblocking（一次性返回）；长任务可改 streaming，但端侧视频更该用队列 + 轮询
userstring账号维度：同一 user 的运行记录与产物互相可见，用于隔离
data.outputs.planstring(JSON)结构化计划，画布 parse 后得到 tasks[] / shots[]
data.outputs.generate_resultstring(JSON)本地出图 API 的回执（accepted / engine / local_only）
data.outputs.task_count / shot_countnumber队列长度，直接渲染到界面
task_idstring配合 POST /v1/workflows/{task_id}/stop 做中断，对应文档 ③

调用示例 · curl

curl -X POST http://127.0.0.1:8765/v1/workflows/run \
  -H 'Content-Type: application/json' \
  -d '{"inputs":{"scene":"ecom","product_name":"保温杯","style":"极简白棚","size":"1:1 主图","sku_count":"6","candidates":"4"},"response_mode":"blocking","user":"studio-local"}'

调用示例 · Python（零依赖）

import json, urllib.request
payload = {"inputs": {"scene": "drama", "script": "夜色，便利店门口。两人对视。",
                      "shot_count": "6", "resolution": "480p 预演",
                      "anchor_lock": "每镜头 re-anchor（推荐）"},
           "response_mode": "blocking", "user": "studio-local"}
req = urllib.request.Request("http://127.0.0.1:8765/v1/workflows/run",
    data=json.dumps(payload).encode("utf-8"),
    headers={"Content-Type": "application/json"})
with urllib.request.urlopen(req, timeout=30) as r:
    outputs = json.load(r)["data"]["outputs"]
plan = json.loads(outputs["plan"])
print(outputs["summary"], "-> 镜头数", len(plan["shots"]))

调用示例 · 浏览器（两个 Demo 里就是这么写的）

const res = await fetch("http://127.0.0.1:8765/v1/workflows/run", {
  method: "POST", headers: {"Content-Type": "application/json"},
  body: JSON.stringify({inputs, response_mode: "blocking", user: "studio-local"})
});
const { data } = await res.json();

// 失败时自动回退到内置编排，界面不会卡住
账号 / 授权怎么落真 Dify 里应用 API Key 只放服务端，绝不写进前端 HTML（官方文档也是这么要求的）；本地验证服务只监听回环、用 no-auth，是为了让作业在课堂上能一键演示，不代表产品里可以省掉鉴权。

07本地编排服务：不装 Dify 也能验证整条链路

local_api_server.py 只用 Python 标准库，双击同目录的 启动本地服务.command 即可；或者命令行执行 python3 local_api_server.py。它同时扮演三个角色：

角色端点谁在调
Dify 工作流 API 形态POST /v1/workflows/run两个 HTML Demo 的画布
DSL 里 HTTP 节点的本机出图 APIPOST /api/ecom/generate、/api/drama/generate导入后的 Dify 工作流
运行记录与中断GET /health、GET /v1/workflows/run/{id}、POST /v1/workflows/{task_id}/stop运维 / 加分项演示

服务会把运行记录增量写到 runtime_state.json，重启后仍可查询——这是文档 ③「三层持久化」在编排层的一个小实证。

必须诚实说清楚的一件事服务默认跑在 --engine mock（作业正式方案）：它是编排层可运行验证器，不加载模型权重、不产出真实图像，只回一份「已排队」的收据。现在额外提供两个可切换驱动：--engine local 接本机 ComfyUI 真出图（推理仍全在本地），--engine cloud 是给没有显卡的机器做开发演示的 DEV ONLY 通道（不进作业正文，详见文档 ⑤）。三种模式共用同一套队列、状态机与回包结构，上层零改动。课堂演示优先用默认离线模式，并主动讲清这个边界——老师问「图呢」，你答的是架构而不是魔术。
Dify 跑在 Docker 里怎么连DSL 里 HTTP 节点默认写 http://host.docker.internal:8765；容器内的 127.0.0.1 指的是容器自己，会连接超时。此时用 python3 local_api_server.py --host 0.0.0.0 启动。若 Dify 和服务都在宿主机上跑，把 URL 改回 127.0.0.1 即可。默认离线模式下只监听本机 / 内网，不向外网发请求；只有显式开 --engine cloud 的开发演示模式才会访问公网（详见文档 ⑤）。

08DSL 导入失败时的手工搭建路径

Dify 版本迭代快，导入 yml 偶尔会因为字段差异失败。照下面 7 步拖一遍，五分钟就能还原，作业不会卡住：

  1. 工作室 → 导入 DSL 文件（或「创建空白应用」→ 选 Workflow）。
  2. 开始节点：按文档 04 节的表添加输入变量（电商 6 个 / 短剧 4 个），变量名必须和 API 的 inputs 键一致。
  3. LLM 节点：模型供应商选 Ollama / OpenAI-API-compatible，指向本机 qwen3:4b；把 DSL 里的 system / user 提示词复制进去。
  4. 代码节点：语言 python3，贴 DSL 里的 code，按 outputs 声明 4 个输出变量与类型，绑定上游变量。
  5. HTTP 请求节点：POST、URL 指向本机 8765、headers 加 Content-Type: application/json、body 选 json 并引用代码节点的 request_json。
  6. 结束节点：加 plan / generate_result / summary / task_count 四个输出。
  7. 连线 → 点「运行」测一次 → 「发布」→ 右上角「访问 API」拿 Key，把域名和 Key 填进调用示例。
导入后 LLM 节点标红是正常的DSL 里写的是 provider: ollama / name: qwen3:4b，和你本机装的名字不一定一样。点进去重选一次模型就好，其他节点不用动。

09两个 HTML Demo 怎么接上这条链路

Demo接入点勾选「接入本地工作流」后服务没启动时
电商素材工作台生成参数面板 →「批量生成」先 POST 工作流 API，用返回的 plan.tasks 展开队列，日志显示回包里的 engine 与任务数自动回退内置编排，界面照常可用，状态灯显示「未连接」
短剧自动化工作台剧本面板 →「解析为结构化分镜」POST 工作流 API，用 plan.shots 覆盖镜头墙，强制 ≤5s 与 re-anchor 状态同步回退到内置示例分镜，不影响后续审片 / 续跑演示
为什么一定要做「失败回退」端侧产品没有云端兜底，任何一环不通都不能把界面卡死——这本身就是文档 ③ 的产品策略。所以 Demo 里接 API 是增强而不是依赖：老师在没启动服务的电脑上双击打开，原型依然是完整可点的。

10这一层怎么回应题干的「账号 / 授权 / 算力调度」

题干里的词落到哪个接口 / 模块具体机制
账号API 的 user 字段 / Dify 终端用户隔离运行记录与产物归属；同一 user 才能查到自己的回包
授权应用 API Key（Bearer）+ 本地服务仅回环Key 只存服务端；端侧再加一层本机模型许可审查（文档 ① 的 Apache 2.0 判断）
算力调度单执行槽队列、优先级、中断、checkpoint文档 ③ 的状态机 + /stop 接口 + Demo 的 P0 插队 / 从 checkpoint 续跑
本地大模型Ollama Qwen3-4B + ComfyUI Z-Image / Qwen-Image文档 ① 的量化档位与显存账，DSL 里的 engine 字段与之严格一致
这层补充在作业里的定位老师要的仍是三份文档 + 一个 demo × 两套。这一层作为 Demo 的「可运行后端」附在后面，既没有把文档数量改乱，又把题干里最容易被忽略的「接入 API」补成了能验证的实物。

11老师可能追问什么

「Dify 不就是云端的吗？」
用自部署社区版（Docker），和创作应用跑在同一台主机；DSL 里所有 URL 都是回环地址。用 Dify Cloud 就违反题设，这一点我主动排除了。
「为什么不用 Dify 自带的结构化输出？」
端侧小模型未必原生支持，退化后仍可能吐不合规 JSON；且 1.14.0 有已知静默失效问题。所以用提示词约束 + 代码节点校验 + 本地规则兜底三层保证。
「这个 API 真能出图吗？」
默认模式不能，也不假装能：它是编排层验证器，验证需求 → 结构化任务 → 本机队列 → 回包这条链路。真机用 --engine local 接 ComfyUI /prompt 就出像素；我另外做了 DEV ONLY 的联网开发通道，在没有显卡的机器上能出真图，但它不属于作业正式方案、也没有任何自动上云的兜底分支。
「和 ComfyUI 的 API 什么关系？」
Dify 管业务编排（拆任务），ComfyUI 管像素生成（跑推理），中间用本机 HTTP 串起来，是上下游不是替代关系。
「用 RunningHub 跑不是更省事吗？」
省事，但它是云端 GPU + 云端 API，接上就等于承认有云端兜底。作业里把它当对照方案主动排除；本机改用 ComfyUI 加载本地权重。真要练手，只用它设计工作流并导出 JSON 再拿回本机跑。

12常见坑与排查

现象原因怎么处理
导入后 LLM 节点标红模型名 / 供应商与本机不一致点进节点重选 Ollama 或 OpenAI-API-compatible 的本地模型
Docker 里 HTTP 节点连接超时容器里的 127.0.0.1 指向容器自己URL 用 host.docker.internal，服务用 --host 0.0.0.0 启动
浏览器 fetch 被拦CORS / Private Network 策略服务已带 CORS 与 Private Network 响应头，已在 Chrome 下实测 file:// 页面直连可用；个别浏览器仍拦就用 python3 -m http.server 打开
想接 RunningHub 出图它是云端 ComfyUI，违反题设改用本机 ComfyUI 加载本地权重；云端最多只用来设计 / 导出工作流 JSON，不参与推理
JSON 解析失败小模型输出带了 Markdown 围栏或多了解释代码节点已去围栏并准备本地规则兜底，不会崩链
结构化输出开关失效Dify 版本差异 / 已知 issue本方案本来就不依赖该开关
Demo 状态灯一直「未连接」服务没启动或端口被占双击 .command 启动；或 --port 9000 并同步改 Demo 里的端口常量
