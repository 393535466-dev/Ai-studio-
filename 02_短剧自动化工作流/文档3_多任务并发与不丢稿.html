分钟级长任务下的双层状态机、分段 checkpoint、按镜头失败隔离与断点续跑。

一页速读

电商跑一张图几秒，短剧跑一个镜头几分钟——任务时长一变，并发策略就得整个重写。核心是把「一个镜头」再切成若干帧段，每段渲染完就存 checkpoint；中断或崩溃只丢当前帧段，已渲染的帧全部保留，重启后从最后一个 checkpoint 续跑，而不是整个镜头从头来。队列按镜头排、审片打回插队首、夜间批量吃满单机；脚本版本、角色锚图、审片批注、帧段进度全部即时落盘。不承诺同时渲染多个镜头，只承诺：一集跑到一半出任何事，都能接着跑完。

01任务时长改变了什么：与电商套装的根本差异

维度电商（秒级任务）短剧（分钟级任务）对策略的影响
单个任务时长5–8 秒1–10 分钟中断代价从「重跑一张」变成「重跑几分钟」
失败粒度整张图即可必须细到帧段需要双层状态机 + 分段 checkpoint
主要瓶颈显存峰值显存带宽、系统内存、NVMe 帧缓存监控项要增加内存、磁盘、温度
用户在线状态通常盯着屏幕常挂机夜间跑需要无人值守、失败可延后处理
人工介入点生成后挑图审片台逐镜头通过/打回人的判断要能回插队列且优先级最高
产品原则① 单卡一次只渲染一个镜头；② 任何已完成的帧段绝不因后续失败而作废；③ 失败隔离到镜头：一个镜头 OOM 不影响其他镜头；④ 所有状态即时落盘；⑤ 绝不静默失败、绝不联网兜底。

02双层状态机：镜头层 + 帧段层

这张图是整套加分项的核心：电商套装只需要任务级状态机，短剧必须再加一层帧段状态机，否则「失败恢复」在分钟级任务上等于没做。

03队列策略：镜头级排队 + 帧段子任务 + 夜间批量

机制设计解决什么
单执行槽一次只渲染 1 个镜头；镜头内部按帧段顺序推进显存带宽与内存争抢
优先级P0 审片打回镜头 ＞ P1 单镜头预览 ＞ P2 关键帧批量 ＞ P3 终稿夜间批量让人的判断优先于机器批量
审片回插打回的镜头带着原锚图与修订批注生成新任务，插到队首；原产物保留为历史版本只重跑该重跑的，且可对比新旧版本
模型亲和性关键帧阶段连跑完再切视频模型；视频阶段尽量不回切图像模型减少 20GB 级模型反复卸载/加载
夜间批量模式用户设定「仅空闲时渲染终稿」；白天空出算力给画布与审片无人值守吃满单机，不干扰白天交互
帧缓存配额每镜头临时帧上限；审片通过即清理临时帧，只留成片与复现参数防止 20 镜头把 2TB 盘写满
预计完成时间按已完成镜头的实测均速动态估算整集剩余时间并显示长任务必须给预期，否则用户会误判卡死
「边生成边编辑」在短剧里的含义不是边渲染边改视频（做不到），而是：后台渲染镜头 5 时，用户可以继续在审片台改镜头 2 的分镜描述、批注、换锚图，改动以 P0 增量任务回插队列。编辑的是脚本与参数，不是正在被 GPU 占用的帧——这样体验上仍然流畅。

04中断策略：按镜头中断，按帧段保留

用户动作系统动作对应本地接口保留什么
取消排队镜头从待渲染列表移除POST /queue {"delete":[prompt_id]}脚本、锚图、分镜、已有关键帧
中断当前镜头停止当前帧段采样，释放显存POST /interrupt已完成的所有帧段 + checkpoint + 参数
切换到终稿档排空预演队列 → 卸载 → 加载精修模型队列编排 + 模型管理全部预演产物保留，不覆盖
关闭应用 / 掉电当前帧段标记中断，其余镜头转可恢复本地快照脚本版本、锚图、批注、队列、帧段
清空夜间批量只清 queued，不动 running，二次确认DELETE /queue所有已落盘帧段与审片结论
与电商的关键差别电商中断后保留「已出完的图」；短剧中断后必须额外保留「已渲染但未拼接的帧段」，否则用户看到的不是「暂停」而是「白跑」。

05失败恢复：分类处理 + 帧段续跑

异常类型恢复动作是否自动
OOMError降分辨率 720p→480p / 帧数 121→77 / 启用分块 VAE，从最后完成的帧段续跑；连续 2 次转人工自动，最多 2 次
ValidationError定位到具体分镜或节点，提示用户修正；不重跑整镜头否，需人工
ModelDownloadError暂停同模型所有镜头，提示补齐本地权重；绝不联网下载否，需人工
磁盘将满暂停新镜头、清理已通过镜头的临时帧、提示用户半自动
温度降频 / 持续高温自动降速并延后终稿批量，保留队列不取消自动
进程崩溃 / 掉电读快照重建队列 → running 转 resumable → 从最后 checkpoint 续跑自动
角色一致性校验失败自动 re-anchor 到原始锚图重出关键帧；视频帧作废但保留参数；仍失败则标「待人工审」自动，1 次
一条容易写错的逻辑「一致性失败」不能只重跑视频：角色是在关键帧阶段就定下来的，视频只是让它动起来。所以恢复动作必须回到关键帧 re-anchor，否则重跑十次还是同一个人漂。这也是双层流水线的意义。

06不丢稿：三层持久化 + 版本化 + 帧缓存生命周期

层存什么时机恢复时怎么用
L1 草稿层剧本文本、分镜表逐条编辑、审片批注、时间线标记每次编辑防抖 300ms 即写重启还原审片现场
L2 参数层分镜 JSON、角色锚图哈希与版本、LoRA/trigger、prompt、seed、模型版本、帧段划分任务入队时写入，只读不可变重建队列、续跑、重出任一镜头
L3 产物层关键帧、每帧段渲染结果、checkpoint、拼接成片每帧段落盘立刻写，不攒批中断后已完成的帧一帧不丢

短剧特有的三条约定

  • 版本化：脚本、角色卡、审片结论都带版本号；打回重生成产生新版本，旧版本不覆盖，方便导演对比「上一版更好」。
  • 幂等：镜头任务 ID = 分镜哈希 + 锚图版本 + 参数 + seed；重复恢复不会产生重复镜头或错序拼接。
  • 帧缓存生命周期：渲染中保留 → 审片通过即清理临时帧 → 只留成片与可复现参数包；磁盘配额到阈值时按「最早且已通过」顺序清理。
验收口径草稿丢失率 = 0、断点续跑成功率 = 100%、单镜头失败不影响其他镜头、中断响应 ≤ 5 秒。与文档 ① 的客观指标一一对应。

07边界与指标

  • 不承诺「同时渲染多个镜头」——单卡物理上限；承诺同时提交、边渲染边审片、按优先级响应。
  • 不承诺实时预览、1080p、长镜头——这些在 24GB 端侧不能稳定交货，产品界面应显式标注。
  • 不承诺模型缺失自愈——离线只能由用户补齐权重文件。
  • 不承诺跨设备同步——账号只做本地使用者区分与授权。
并发指标目标值
单镜头失败隔离率100%（其他镜头不受影响）
中断后已渲染帧保留率100%
断点续跑成功率100%
草稿 / 脚本 / 锚图丢失率0
帧缓存峰值占用≤ 40GB
预计完成时间误差≤ 20%

08老师可能追问什么

「为什么不用最强的 FLUX.2？」
两个硬理由：社区许可非商用（电商/短剧都是要交货的），且 32B 模型 33.8GB 超出 24GB 显存，offload 后单张要几分钟，端侧批量不现实。
「没有云端兜底，慢了怎么办？」
答降级阶梯：降分辨率 → 减步数 → 卸载大模型 → 暂停后台保前台 → 明确拒绝并提示。绝不静默失败，也绝不偷调云 API。
「主观效果怎么算评估？」
答盲测 + 5 分制评分表 + 多人取均值 + 锚图 A/B + 固定 seed 可复现。主观维度也要可操作、可复议。
「并发不就是把任务排队吗？」
答四层：状态机、优先级与配额、按错误类型分类恢复、三层持久化（草稿 / 参数 / 产物）。排队只是第一层。
