一页速读

短剧比电商难得多：一个镜头要跑几分钟，端侧最吃力。所以我的策略是「把场景裁剪到端侧能胜任的范围」：分镜脚本用本地 Qwen3-4B 生成结构化表；关键帧用 Z-Image-Turbo 快速出；角色用锚图 + 角色 LoRA + 姿态控制钉住；视频只做 5 秒以内的图生视频，主力 Wan2.2 TI2V-5B 的 GGUF 版本和 LTX-Video FP8，不碰 14B 大模型。一致性的死规矩是：每个镜头都回到原始角色锚图，绝不拿上一镜头的输出当参考（否则脸会一路漂走）。质量和速度冲突时仍然保速度，因为批量出片是长任务，而且没有云端能接手。

01前提假设与场景裁剪

沿用套装 A 的硬件假设，但短剧对系统内存和磁盘的要求更高。

项目假设规格为什么这样假设
GPU单卡 24GB 显存（RTX 4090 档；32GB 为可选高配）2026 年本地创作主机的主流档位；24GB 是 FP8 大模型的实际门槛
系统内存64GB DDR5视频工作流的 T5-XXL 文本编码器常需 offload 到内存，10–20GB
存储2TB Gen4 NVMe（≥5000 MB/s）模型加载、帧缓存、草稿落盘都吃磁盘；首图慢主要是加载而非计算
网络完全离线，无外网、无云端兜底题目硬约束；所有失败只能在本地消化
使用方式单机单卡，本地账号区分使用者对应题干的「账号 / 授权 / 算力调度」平台能力
显存预算峰值 ≤ 20GB，预留 4GB 给画布、VAE 解码与激活留余量是避免 OOM 的第一道工程约束
诚实的前提：端侧不适合「完整短剧自动化」24GB 单卡跑 720p 的 5 秒片段，LTX / Wan2.2-14B FP8 大约要 2–5 分钟，HunyuanVideo 约 5–10 分钟；而云端同类片段只要 30–90 秒。如果原样照搬「长镜头 + 高分辨率 + 实时预览」，这个场景在端侧根本不成立。
所以产品判断是主动裁剪场景边界：竖屏 9:16、单镜头 ≤ 5 秒、480p 预演 / 720p 终稿、以图生视频（I2V）为主而非纯文生视频、批量任务允许夜间离线跑。把场景定义成「端侧能稳定交货的短镜头批量产线」，它才是一个适合端侧的场景。这句话就是题目要的「判断理由」。
视频场景的两条额外硬件约束① 系统内存 64GB 是必需的：T5-XXL 一类文本编码器 10–20GB 常需 offload 到 CPU 内存，32GB 会触发磁盘交换，速度塌方。② Gen4 NVMe 是必需的：5 秒 720p 片段会产生数 GB 临时帧，SATA 盘会直接成为瓶颈。

02选型结论：一条「脚本 → 关键帧 → 短镜头」的本地流水线

环节推荐模型 / 组件精度 / 量化版本选型理由
分镜脚本结构化Qwen3-4B-Instruct（本地小语言模型）GGUF Q4_K_M把剧本文本解析成结构化 JSON（镜头号 / 景别 / 人物 / 动作 / 时长 / 提示词），纯本地、秒级，不联网
关键帧 / 分镜图Z-Image-Turbo（6B）GGUF Q5_K_S8 步、约 5 秒/张、Apache 2.0 可商用；先把图定下来再动视频，避免在视频上反复试错
角色一致性（图像侧）FLUX.2 klein 4B 参考图编辑（Apache 2.0）
+ 角色 LoRA + ControlNet OpenPose		fp16 / 参考图权重 0.6–0.8多参考图保持身份、姿态可控；避开 InstantID / PuLID 依赖的 InsightFace 非商用权重
图生视频主力Wan 2.2 TI2V-5BGGUF Q4_K_M / Q5_K_M + offloadApache 2.0 可商用；5B 变体 6–8GB 显存可跑，是端侧能吃下的档位
快速预演 / 审片LTX-Video 2.3FP8，480p 约 6–8GB速度最快，用于导演审片与动作预演，不用于终稿
终稿精修（可选）HunyuanVideo 1.5（8.3B）FP8，720p 约 16GB / 24GB 推荐腾讯混元社区许可；画质更好但 5 秒片段要 5–10 分钟，只对通过的镜头启用
帧处理与拼接本地 FFmpeg + 帧插值 / 分块 VAE—纯本地后处理，不涉及任何外部服务
运行框架ComfyUI + ComfyUI-GGUF + VideoHelperSuite—图像与视频共用一套工作流与队列接口，便于统一调度
为什么是「图先行」而不是直接文生视频端侧视频生成一分钟起步，直接拿脚本试错的代价太高。先把每个镜头的关键帧（静态图）快速定稿、让导演审过，再只对通过的镜头做 I2V——把昂贵的视频算力集中在已经确认的镜头上。这是无云端兜底环境下最有效的成本压缩。
明确不选什么Wan2.2-14B BF16（官方脚本需 80GB 级显存）、FLUX.2 dev（非商用 + 超显存）、InstantID / PuLID（许可风险）、1080p / 长镜头 / 实时预览（端侧体验不成立）、任何云端视频 API（违反题设）。

03算力账：把「一集要多久」算给用户看

环节配置显存 / 内存单件耗时（4090 24GB 量级）
脚本 → 分镜表Qwen3-4B Q4约 3GB秒级
关键帧生成Z-Image-Turbo Q5，1024² 8 步约 10GB5–8 秒/张
480p 预演片段LTX-Video 2.3 FP8，5 秒6–8GB约 1–2 分钟
720p 终稿片段Wan2.2 / HunyuanVideo 1.5 FP8，5 秒16–24GB + 内存 offload约 3–10 分钟
20 镜头整集按 1 预演 + 1 终稿估算—约 1.5–3 小时，适合夜间批量

两条必须写进产品规格的物理规律：显存随分辨率近似二次方增长，随时长/帧数/步数近似线性增长。因此 MVP 把分辨率和时长锁死，而不是让用户随便填——这既是性能保护，也是产品约束设计。

别回避端侧的劣势云端同类 5 秒片段 30–90 秒，端侧慢一个数量级。产品上不靠「假装很快」解决，靠批量离线、预期时间可见、夜间跑、分段 checkpoint来解决。把这个劣势摆到台面上并给出对策，比回避它更得分。

B. 需主观评测（给出可执行协议）

维度评测协议通过线
角色身份一致性跨 10 个镜头并排，5 人盲测「是否同一人」5 分制；重点看侧脸、全身、逆光均值 ≥ 4.0，严重换脸 = 0
时序质量五轴参照 VBench 式分解：运动平滑度、时序闪烁、主体身份一致性、动态程度、成像质量，逐项评分各轴 ≥ 3.5 / 5
分镜脚本可执行性导演/编导评「景别、动作、时长是否可直接照拍」均值 ≥ 4.0
镜头连贯性相邻镜头拼接后看光线、服装、场景是否跳戏均值 ≥ 3.8
成片可用率二分类「可直接进剪辑 / 需重生成」≥ 60%（端侧目标，低于云端但可接受）
一致性的头号工程纪律：re-anchor固定 seed 只在「什么都不变」时能复现角色；一旦换姿势、换场景，同一 seed 也会生成另一张脸。所以每个新镜头都必须回到最初那 3–5 张角色锚图做参考，绝不能把上一镜头的输出当作下一镜头的参考——串联输出会让细微误差逐镜累积，十几个镜头后角色就换人了。这一条同时写进模块设计与验收标准。

05质量 vs 速度只能保一个：仍然保速度

结论：默认保速度（出片节奏与批量吞吐）理由 1：短剧是典型的批量出片，20 个镜头串行；在端侧单卡上，单镜头从 3 分钟变成 8 分钟，整集就从 1 小时变成近 3 小时，交付节奏直接崩掉。
理由 2：无云端兜底，慢了没有第二台机器可加，只能靠「夜间离线批量」消化，而这个窗口是有限的。
理由 3：视频是长任务，中途失败代价极高；追求极致质量会推高 OOM 与中断概率，反而降低整集完成率。
理由 4：质量损失可用「关键帧人工挑 + 只重生成打回镜头 + 后期调色/插帧」补偿；速度损失没有补偿手段。

产品上的分层：预演档 / 终稿档

默认全流程走快速预演档（LTX 480p）供导演审片；只有审片通过的镜头才允许用户显式标记为终稿，切到 720p 精修。即「系统默认值保速度，个别镜头允许买质量」，把有限算力花在真正会交付的镜头上。

反方观点若客户是品牌定制短剧、单条报价高、镜头数少，应保质量。取舍依据仍然是客户结构与交付物类型，不是模型参数。

06无云端兜底下的降级阶梯

级别触发条件系统动作用户可见
L0资源充足按预演/终稿档正常排队正常进度 + 预计完成时间
L1显存告警720p → 480p、帧数 121 → 77提示已降档，可手动改回
L2内存吃紧 / 温度偏高文本编码器 offload 到内存、降低并发槽、自动降速「已自动降速以保护稳定性」
L3批量积压严重只保留 I2V 关键帧，暂停新镜头视频渲染队列显示哪些镜头待渲染
L4审片台正在操作前台审片/批注优先，后台渲染降为低优先级算力让出提示
L5磁盘帧缓存将满 / 持续 OOM降级为「分镜图交付」：先交关键帧故事板，视频任务转入待办明确说明：不静默失败，交付不中断
L5 是这套方案的关键设计端侧最坏情况下也要有东西可交。与其让整集卡死在渲染，不如降级交付分镜故事板 + 保留视频任务队列，用户第二天补跑。这是「无云端兜底」倒逼出来的产品韧性。

08老师可能追问什么

「为什么不用最强的 FLUX.2？」
两个硬理由：社区许可非商用（电商/短剧都是要交货的），且 32B 模型 33.8GB 超出 24GB 显存，offload 后单张要几分钟，端侧批量不现实。
「没有云端兜底，慢了怎么办？」
答降级阶梯：降分辨率 → 减步数 → 卸载大模型 → 暂停后台保前台 → 明确拒绝并提示。绝不静默失败，也绝不偷调云 API。
「主观效果怎么算评估？」
答盲测 + 5 分制评分表 + 多人取均值 + 锚图 A/B + 固定 seed 可复现。主观维度也要可操作、可复议。
「并发不就是把任务排队吗？」
答四层：状态机、优先级与配额、按错误类型分类恢复、三层持久化（草稿 / 参数 / 产物）。排队只是第一层。
