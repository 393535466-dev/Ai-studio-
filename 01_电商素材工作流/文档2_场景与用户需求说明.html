一页速读

电商卖家/设计工作室每天要出几十上百张图：同一件商品换场景、换风格、改尺寸，还不能让商品变样。这些活重复、批量、离线、素材还保密，正好是端侧最擅长的。MVP 只做一条闭环：导入商品图 → 钉住商品当锚 → 套风格模板 → 批量排队生成 → 在画布上边生成边改 → 一键导出多尺寸。不做什么比做什么更重要：不做视频、不做复杂 3D、不做协作云同步。

01场景与用户需求

用户画像

电商商家 / 运营
上新快、SKU 多，需要主图、场景图、详情图；自己不会写提示词，只想「选个模板、上传商品、出图」。
小型设计工作室
同时服务多个客户，最怕商品被 AI 画变形、LOGO 错位；客户素材不能上传到外部平台。
内容创作者
一次活动要出十几张同风格图，还要 1:1 / 3:4 / 9:16 多平台尺寸，手动改尺寸极其耗时。

Jobs-to-be-Done（用户真正雇这个产品做什么）

用户说法真实需求当前痛点
「把这件衣服放到沙滩上」主体保持 100% 一致，只换场景与光影通用生图会把衣服的花色、领口、LOGO 画变
「6 个颜色一起出」多 SKU 之间只能变颜色，其他完全一致逐张生成导致风格漂移，像 6 件不同商品
「主图、详情、短视频封面都要」一次生成，自动派生多尺寸多比例手工裁切+重排版，重复劳动
「客户图不能外传」素材与生成全过程留在本地云端生图工具存在素材外泄与合规风险
「今天下班前要」批量吞吐可预期，别中途崩掉跑到一半失败、草稿丢失、要全部重来
为什么这个场景适合端侧（题目的「判断理由」）① 素材保密是刚需：未上架新品、客户品牌素材不适合上传第三方云端，本地推理天然满足。
② 任务可离线、可排队：批量出图不需要实时交互，适合在后台按队列慢慢跑，把单机算力吃满。
③ 图片为主，算力可控：8 步 Turbo 模型在 24GB 卡上 5–8 秒/张，不像视频生成那样动辄几分钟一个镜头，端侧体验能达标。
④ 成本结构合理：高频、重复的批量任务摊薄硬件成本；不像偶发任务那样用云更划算。
⑤ 产物可复现：seed + 参数 + 锚图全部本地存档，客户要「再出一张一样的」随时能重放。

02MVP 范围：先做一条能交货的闭环

MVP 做
① 单商品图导入与自动抠图
② 商品锚图 + 一致性控制
③ 风格 / 场景模板（内置 6 套）
④ 批量任务编排（多 SKU × 多尺寸）
⑤ 画布编辑（局部重绘、改词、换背景）
⑥ 多尺寸导出与上架前校验
⑦ 草稿自动保存与队列恢复
MVP 明确不做
× 视频生成（交给另一套场景方案）
× 多人实时协作 / 云同步
× 自定义模型训练界面
× 复杂 3D 建模与材质
× 无限并发（单卡物理上限，不承诺）
× 任何需要联网的功能
范围判断的依据MVP 的取舍标准是「能不能独立完成一次完整交货」，而不是功能多。少一个模块就交不了货的，必须做；只是锦上添花的，一律后置。

03核心模块拆解：每个模块解决什么问题、怎么协作

#模块解决什么问题输入 → 输出依赖 / 下游
M1商品资产库把散落的商品图、SKU 表、品牌规范集中管理，避免每次重传；也解决「素材不出本地」商品图 + SKU 清单 → 结构化商品对象（含锚图）为 M2 提供锚图；为 M4 提供批量清单
M2一致性引擎本场景最关键：保证商品不变形、多 SKU 之间只变该变的东西锚图 + 目标风格 → 带 IP-Adapter / LoRA 约束的工作流参数输出给 M4 编排；M5 改图时复用同一锚
M3模板与提示词中心用户不会写提示词；把风格、场景、光影、平台尺寸沉淀成可复用模板模板选择 + 少量填空 → 结构化 prompt + 参数组为 M4 提供参数；模板本身可版本化
M4批量任务编排把「6 色 × 3 尺寸」展开成任务 DAG，处理排队、优先级、模型切换、失败重试商品清单 × 模板 → 有序任务队列调用本地推理 API；向 M6 回报状态
M5画布编辑器「边生成边编辑」：用户在批量跑的同时挑图、局部重绘、改一句话重出已出图 + 用户编辑 → 增量任务（只重跑改动部分）增量任务插回 M4，优先级高于后台批量
M6导出与交付校验自动派生 1:1 / 3:4 / 9:16，检查尺寸、文字错漏、商品一致性，打包交付成品图 → 多尺寸文件包 + 校验报告消费 M4/M5 产物；写回资产库存档
M7草稿与恢复中心横切模块：草稿、参数、产物三层落盘；崩溃后重建队列所有编辑与任务状态 → 本地持久化快照被 M1–M6 共同调用（详见文档 ③）
模块协作的一条核心设计M5 画布编辑不直接调模型，而是生成「增量任务」回插 M4，并给更高优先级。这样只用一套队列、一套显存账，用户改一张图不会和后台批量抢 GPU。

04端到端工作流（对应 Demo 里能点的每一步）

导入商品图→自动抠图 / 设锚→选风格模板→展开 SKU × 尺寸→批量排队→本地生成→画布挑图改图→导出校验
步骤用户动作系统动作状态落盘
1拖入商品图 / SKU 表抠图、生成锚图、写入资产库锚图 + 原始图哈希
2选场景与风格模板加载模板，生成结构化 prompt 与参数组模板版本号 + 参数快照
3勾选 6 色 × 3 尺寸展开为 18 个任务，写入队列（含 seed）workflow_api.json + 任务清单
4点「开始批量」单卡串行执行；前台编辑可插入高优先级任务每个任务的状态与进度
5边跑边在画布挑图对不满意的图局部重绘 / 改词，生成增量任务增量任务 + 编辑历史
6一键导出派生多尺寸、跑一致性/文字校验、打包成品 + 校验报告 + 复现包

05关键页面与交互说明（Demo 的对应关系）

页面区域关键交互要体现的产品决策
左：商品与 SKU 列表点选 SKU，画布切换；显示锚图锁定标记锚图是全局唯一真相源，任何生成都 re-anchor 到它
中：画布切换候选图、局部涂抹重绘、改提示词重出「边生成边编辑」；编辑产生高优先级增量任务
右：参数面板风格、场景、尺寸、候选数、质量档位默认快速档（保速度），精修档需显式开启并提示耗时
底：任务队列进度条、暂停、中断、模拟失败、一键恢复队列状态机与失败恢复（文档 ③ 的可视化）
顶：算力条显存占用随任务数变化，超阈值触发降级提示端侧资源是全局共享的，必须对用户可见
全局：自动存稿灯刷新页面后草稿、参数、队列仍在三层持久化，不丢稿
为什么把「算力占用」放在界面上云端产品可以隐藏资源，端侧不行。用户必须知道「为什么变慢了 / 为什么队列停了」，否则会把降级误判为软件坏了。这是端侧产品特有的透明度设计。

06MVP 验收标准

验收项标准
闭环完整从导入一张商品图到导出多尺寸文件包，全程不依赖任何联网操作
一致性6 色 SKU 盲测「是否同一商品」均值 ≥ 4.2；LOGO / 形状零错误
批量效率18 张任务 ≤ 3 分钟完成，中途可编辑、可中断、可恢复
不丢稿强制结束进程后重启，草稿与队列 100% 还原
可复现任一张成品可用存档的 seed + 参数重出同一张图

07与短剧场景的差异（为什么两套方案不能合并写）

维度电商素材短剧自动化
产物静态图，秒级单张视频镜头，分钟级单段
算力瓶颈显存余量与模型切换显存带宽、系统内存、磁盘帧缓存
一致性对象商品本体（形状 / LOGO / 配色）人物身份 + 服装 + 跨镜头场景
失败代价重跑一张，成本低重跑一个镜头要几分钟，必须按镜头 checkpoint
并发策略短任务高频排队长任务分段、夜间批量、断点续跑

正因为这些差异，模型选型、模块划分、并发策略都要各自成篇——这也是把两套交付分开做的原因。

08老师可能追问什么

「为什么不用最强的 FLUX.2？」
两个硬理由：社区许可非商用（电商/短剧都是要交货的），且 32B 模型 33.8GB 超出 24GB 显存，offload 后单张要几分钟，端侧批量不现实。
「没有云端兜底，慢了怎么办？」
答降级阶梯：降分辨率 → 减步数 → 卸载大模型 → 暂停后台保前台 → 明确拒绝并提示。绝不静默失败，也绝不偷调云 API。
「主观效果怎么算评估？」
答盲测 + 5 分制评分表 + 多人取均值 + 锚图 A/B + 固定 seed 可复现。主观维度也要可操作、可复议。
「并发不就是把任务排队吗？」
答四层：状态机、优先级与配额、按错误类型分类恢复、三层持久化（草稿 / 参数 / 产物）。排队只是第一层。
