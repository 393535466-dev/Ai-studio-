文档 ③ · 多任务并发与不丢稿｜电商素材工作流

多任务并发下的队列、中断、失败恢复与草稿持久化策略；对应 Part 2 加分项。

场景：电商素材工作流加分项对应交付对标 ComfyUI 真实 API配套：Demo 底部队列面板

一页速读

单机单卡最怕的不是「慢」，是「跑到一半崩了、稿子没了」。我的策略是四层：① 所有任务进同一个队列、单卡串行执行，前台编辑优先；② 每个任务有明确状态机，中断要能立刻释放显存；③ 失败按错误类型分别处理——显存不足就自动降配重试，模型缺失就暂停等人补文件，绝不盲目重跑；④ 草稿、参数、产物三层即时落盘，进程被强杀后重启能重建队列。不承诺无限并发，只承诺一张稿都不丢。

01问题定义：端侧并发到底在冲突什么

「多任务并发（同时生成多张、边生成边编辑）」在端侧不是软件问题，是资源问题。先把冲突列清楚，策略才有针对性。

显存争抢
两个生成任务同时进来，激活内存叠加直接 OOM；本地没有第二张卡可以分担。
模型切换争抢
批量用 Turbo、中文主图用 Qwen-Image，两个 20GB 级模型同驻会撑爆内存，切换还要几十秒。
前台 / 后台争抢
用户正在画布上涂抹重绘，后台 18 张批量还在跑 → 用户操作卡顿，体感是「软件卡死」。
失败放大
云端失败可以换机器重试，端侧一次 OOM 可能让整批任务一起失败，且草稿没存就全没了。
产品原则（先立规矩）① 不做 GPU 硬并发：单卡一次只跑一个生成任务，并发体现在「排队 + 可编辑 + 可插入」而不是同时占显存；② 前台优先；③ 任何写操作即时落盘；④ 绝不静默失败，每个异常都要给用户可见的状态与下一步。

02任务状态机：所有并发行为的共同语言

状态机不是画着好看：它决定了「什么能取消、什么能恢复、什么必须重来」，也决定了界面上每个按钮该不该亮。

03队列策略：单卡串行 + 优先级 + 模型亲和性

机制设计解决的冲突
单执行槽GPU 一次只跑 1 个生成任务，其余排队；用户看到的是「同时提交多张」而非「同时占用显存」显存争抢 / OOM
优先级P0 前台编辑（局部重绘、改词重出）＞ P1 单张预览 ＞ P2 后台批量 ＞ P3 预生成缓存前台 / 后台争抢
可抢占点在采样步之间、任务边界处允许插入 P0；不在单张采样中途抢占既保证响应，又避免半成品
模型亲和性分组把使用同一模型的任务成批连跑，减少卸载/加载；切换精修模型前先排空 Turbo 队列模型切换开销
配额与公平单用户后台批量最多占 80% 时间片；批量任务每 N 张让出一次给 P0避免一个批量把整机锁死
重复提交拦截相同锚图 + 参数 + seed 的任务在 5 秒内重复提交直接复用结果用户焦虑性连点造成队列雪崩
算力可见队列页常驻显示显存、执行槽、排队数、降级级别端侧特有的透明度
为什么「边生成边编辑」依然成立用户不需要 GPU 真的并行：编辑操作（挑图、涂抹、改词、排版）本身不吃显存，只生成「增量任务」插到队首。体感是边跑边改，物理上仍是单卡串行——这是端侧产品最重要的一个体验设计。

04中断策略：区分「取消排队」和「打断正在跑的」

用户动作系统动作对应本地接口结果
取消某个排队任务从待执行列表移除，不改 GPU 状态POST /queue {"delete":[prompt_id]}任务 → cancelled，草稿保留
停止当前生成中断正在执行的采样，立即释放显存POST /interrupt任务 → interrupted，参数与已完成产物保留
清空后台批量只清 queued，不动 running；需二次确认DELETE /queue批量清空，画布草稿不受影响
切到精修模式先中断 / 排空 Turbo 队列 → 卸载 → 加载 Qwen-Image队列编排 + 模型管理界面显示切换耗时，不静默
用户关闭应用运行任务标记 interrupted 并写 checkpoint，下次启动询问是否续跑本地状态持久化不丢稿
细节分中断后已生成的部分候选图仍然保留：4 张候选跑到第 3 张被中断，前 2 张照样能看、能挑、能导出。很多原型只做「全部作废」，那就不叫不丢稿。

05失败恢复：按错误类型分类，而不是无脑重试

盲目重试在端侧很危险：OOM 的任务原样重跑只会再 OOM 一次。必须先看异常类型（本地推理服务会通过执行事件给出分类），再决定动作。

异常类型含义恢复动作是否自动
OOMError显存不足降分辨率 → 减候选数 → 分块 VAE，参数改写后重新入队；连续 2 次失败转人工自动，最多 2 次
ValidationError工作流 / 参数非法不重试，定位到具体节点，提示用户修正模板否，需人工
ModelDownloadError模型文件缺失或损坏暂停同模型的所有任务，提示补齐本地权重；绝不尝试联网下载否，需人工
ImageDownloadError输入图读取失败回退到资产库里的锚图副本重试一次自动，1 次
磁盘将满 / 写入失败本地存储问题暂停队列、清理临时帧缓存、提示用户半自动
进程崩溃 / 掉电整机级别中断重启后读快照 → 重建队列 → running 转 resumable → 从最后一个 checkpoint 续跑自动
商品一致性校验失败产物质量不合格（主观维度的自动化代理）自动 re-anchor 到原始锚图重出一版，仍失败则标记为「待人工挑」自动，1 次
无云端兜底在这里的具体含义「模型缺失」这一类错误的正确反应是暂停并告诉用户去拷贝权重文件，不是自动联网下载、更不是切到云 API。这条最能体现端侧意识。

06不丢稿：三层持久化 + 幂等复现

层存什么时机恢复时怎么用
L1 草稿层画布状态、图层、涂抹蒙版、用户编辑历史每次编辑防抖 300ms 即写本地快照重启直接还原画布，用户无感
L2 参数层workflow_api.json、prompt、seed、锚图哈希、模板版本、模型版本任务入队时一次性写入，只读不可变重建队列、重出同一张图、追溯「这张图怎么来的」
L3 产物层每张成品图、中间候选、checkpoint每张出图立即落盘（增量，不攒批）中断后已完成的图不丢；失败任务从最后一张续

三个让「不丢稿」真正成立的工程约定

  • 幂等：任务 ID 由「锚图哈希 + 参数 + seed」生成，重复提交或重复恢复不会产生第二份产物。
  • 可复现：固定 seed + 固定模型版本 + 固定参数，随时能重出客户要的那张图；这也是主观评测能复议的前提。
  • 写前日志：先记「即将做什么」再执行，崩溃时才知道断在哪一步，而不是靠猜。
验收口径草稿丢失率 = 0、崩溃恢复成功率 = 100%、中断响应 ≤ 3 秒。这三个数字写进文档 ① 的客观指标里，形成闭环。

07边界：明确不承诺什么

  • 不承诺「同时跑 N 个生成任务」——单卡物理上限，承诺的是同时提交、边跑边改、按优先级响应。
  • 不承诺模型缺失能自愈——离线环境下只能由用户补文件。
  • 不承诺无限队列——磁盘与显存都有上限，达到阈值走降级阶梯 L5 明确拒绝新任务。
  • 不承诺跨设备同步——账号只做本地使用者区分与授权，不做云同步。

把边界写清楚，比把功能写满更像一个真正做过端侧产品的 PM。

08老师可能追问什么

「为什么不用最强的 FLUX.2？」
两个硬理由：社区许可非商用（电商/短剧都是要交货的），且 32B 模型 33.8GB 超出 24GB 显存，offload 后单张要几分钟，端侧批量不现实。
「没有云端兜底，慢了怎么办？」
答降级阶梯：降分辨率 → 减步数 → 卸载大模型 → 暂停后台保前台 → 明确拒绝并提示。绝不静默失败，也绝不偷调云 API。
「主观效果怎么算评估？」
答盲测 + 5 分制评分表 + 多人取均值 + 锚图 A/B + 固定 seed 可复现。主观维度也要可操作、可复议。
「并发不就是把任务排队吗？」
答四层：状态机、优先级与配额、按错误类型分类恢复、三层持久化（草稿 / 参数 / 产物）。排队只是第一层。
