一页速读（能用大白话讲出来就行）

这台机器只有 24GB 显存、还不能上网。所以我选了一个又能商用、又跑得快、又省显存的小模型 Z-Image-Turbo 当主力（压缩成 GGUF Q5），只有需要「图上写中文」时才临时切到 Qwen-Image。商品不许变形，就用参考图 + IP-Adapter 把商品「钉」住，只换背景。评估分两类：能用数字量的（显存、秒数、成功率）和得靠人看的（像不像、能不能直接上架），后者也要用盲测评分表。最后质量和速度只能保一个，我保速度——因为用户是靠批量交货赚钱的，而且慢了没有云端能救。

01前提假设：先把「机器」说清楚

题目没有给硬件配置，而端侧选型脱离硬件就是空谈。以下假设是本文所有决策的前提，若课上给的机型不同，只需替换这张表并重算显存账。

项目假设规格为什么这样假设
GPU单卡 24GB 显存（RTX 4090 档；32GB 为可选高配）2026 年本地创作主机的主流档位；24GB 是 FP8 大模型的实际门槛
系统内存64GB DDR5视频工作流的 T5-XXL 文本编码器常需 offload 到内存，10–20GB
存储2TB Gen4 NVMe（≥5000 MB/s）模型加载、帧缓存、草稿落盘都吃磁盘；首图慢主要是加载而非计算
网络完全离线，无外网、无云端兜底题目硬约束；所有失败只能在本地消化
使用方式单机单卡，本地账号区分使用者对应题干的「账号 / 授权 / 算力调度」平台能力
显存预算峰值 ≤ 20GB，预留 4GB 给画布、VAE 解码与激活留余量是避免 OOM 的第一道工程约束
贯穿全文的红线所有推理在本地完成，无云端兜底。因此：不能设计任何「本地跑不动就调云 API」的逻辑；性能不足只能在本地做降级、排队、取消或拒绝。文中所有方案都不依赖外网。

02选型结论：一套「主力 + 精修 + 一致性」的组合，而不是一个万能模型

端侧单卡最忌讳「一个大模型包打天下」：大模型常驻会把显存吃满，批量任务全部排队甚至 OOM。正确做法是按任务分层，让便宜的模型承担 90% 的量。

角色推荐模型精度 / 量化版本选型理由
主力出图（约 90% 任务）Z-Image-Turbo（6B）GGUF Q5_K_S（约 5.2GB）
+ Qwen3-4B 文本编码器 Q5_K_M（约 2.9GB）		8 步蒸馏、约 5 秒/张；Apache 2.0 可商用；量化后 8–12GB 显存即可跑，留足余量给批量
精修 / 中文主图Qwen-Image-2512（约 20B）fp8_e4m3fn（峰值约 22GB，需独占串行）中文文字渲染近乎完美；Apache 2.0 可商用。只在「图上要有字」时切换，用完即卸载
商品一致性IP-Adapter（普通版，非 FaceID）
+ 商品 LoRA / 蒙版重绘		adapter fp16；权重 0.6–0.8，end_at≈0.8把商品锚图作为条件注入，只换背景不动主体；避开 FaceID 系的非商用限制

运行框架ComfyUI + ComfyUI-GGUF (city96)—工作流可导出 workflow_api.json；自带队列 / 中断 / 历史接口，正好对应加分项
提示词扩写（可选）Qwen3-4B GGUF Q4_K_M本地小语言模型纯本地，把「白色背景 + 高级感」扩写成结构化提示词，不联网
为什么是这套：四个理由① 许可可商用：电商素材要交付给客户，FLUX.1/FLUX.2 dev 社区许可为非商用，InstantID / PuLID 依赖的 InsightFace 权重同样只允许非商用研究，全部排除。② 显存账算得过来：主力约 8GB 常驻 + 4GB 余量，精修模型单独占用、不与主力同驻（两个 >20GB 模型同时加载会直接把 ComfyUI 撑崩）。③ 吞吐够：8 步 Turbo 模型适合 50 SKU × 3 尺寸这类批量活。④ 可复现：ComfyUI 的 API JSON + seed 可落盘存档，同参数能重出同一张图，这是「不丢稿」的技术基础。
明确不选什么（这部分往往比选什么更能体现判断力）FLUX.2 dev（非商用 + 超显存 + 单张数分钟）、InstantID / PuLID（许可风险）、SD1.5（画质达不到商用）、任何云端 API（违反题设）、多模型常驻（显存打架）。

03显存账与性能预算：把「跑得动」算出来

端侧产品经理必须会算这笔账，否则「推荐具体模型」就只是一句口号。

场景常驻内容峰值显存估算预期耗时并发策略
批量出图（默认）Z-Image-Turbo Q5 + Qwen3-4B Q5 + VAE + IP-Adapter约 10–13GB1024² / 8 步 ≈ 5–8 秒/张单卡串行，批量排队；模型不切换
中文主图（精修）Qwen-Image-2512 fp8 + 文本编码器 + VAE约 22GB约 27 秒/张独占：暂停批量队列，跑完卸载再恢复
2K 以上输出在上述基础上 + 分块 VAE / 放大器+2–3GB+5–10 秒自动降为分块解码，不做整张解码
冷启动模型从 NVMe 载入显存—首图 1–4 分钟开机预热 + 模型常驻，避免每张重载
最容易翻车的一处大模型务必串行加载、用完卸载。两个 20GB 级模型同时驻留会撑爆显存 + 内存。这也直接决定了第 03 份文档里的队列策略：队列不只是排任务，还要排「模型切换」。

A. 可客观测量 —— 机器说了算，可写进验收单

B. 需主观评测 —— 人说了算，但必须给方法

很多作业在这里只写「看效果好不好」，等于没答。正确做法是把主观判断也做成可执行的评测协议：固定样本、随机顺序、多人盲测、锚图对照、评分表留档。

维度评测协议通过线
商品保真度以原始商品图为锚，A/B 盲测 20 组；5 位评审 5 分制；检查 LOGO、形状、配色、材质均值 ≥ 4.0，且「认错商品」= 0
多 SKU 一致性同系列 6 个颜色并排，评「是否同一件商品 / 同一套视觉」均值 ≥ 4.2
提示词遵循度固定 30 条提示词清单（含否定词、材质词、构图词）均值 ≥ 4.0
商用可用率资深设计师二分类：「可直接上架 / 需返工」可直接上架 ≥ 70%
风格一致性同一风格 LoRA 下跨场景出图并排比对均值 ≥ 4.0
中文文字正确率Qwen-Image 生成含文案主图，人工校对错别字与缺字≥ 98%
评测协议的三条纪律① 固定 seed 与固定提示词集，否则两次评测不可比；② 每次都回到原始锚图（re-anchor），不要把上一张生成图当下一张的参考，否则细微偏差会累积成「商品变样」；③ 随机打乱顺序 + 盲测，避免评审知道哪张是新方案。

05质量 vs 速度只能保一个：我保速度

这是产品判断题，不是技术判断题。答案没有对错，但理由必须扣住题干给的目标用户与硬约束。

结论：默认保速度（吞吐与交付时效）理由 1 · 用户价值：目标用户是靠批量交货的图像创作者，收入 ≈ 可交付张数 × 准时率。一张「惊艳但迟到」的图，商业价值低于一百张「够用且按时」的图。
理由 2 · 端侧物理约束：24GB 是硬上限。追求极致质量意味着更大模型、更多步数、更高分辨率，会直接吃掉并发余量，轻则整批变慢，重则 OOM 导致整批失败——而本地没有第二台机器可以接手。
理由 3 · 无云端兜底：云端产品慢了还能加机器，端侧慢了用户只能干等，且这个损失无法转移、无法补救。
理由 4 · 损失可补偿性不对称：速度优先带来的画质损失，可用「多出几张候选 + 人工挑 + 局部重绘 + 放大」补回来；而速度损失没有任何本地补偿手段。

但产品上不做成「一刀切」

更成熟的答法是把取舍交给场景：默认走 Turbo 快速通道；当任务被标记为「品牌 KV / 高客单主图」时，用户可显式开启精修模式（单张独占 Qwen-Image、暂停后台批量、界面明确告知预计耗时）。也就是：系统默认值保速度，个体任务允许临时选质量。这既不违反「只能保一个」的提问，又体现了产品经理对真实工作流的体谅。

反方观点（提前想好，老师可能追问）若目标客户是奢侈品 / 美妆品牌，单张主图的质感直接决定转化率，此时应保质量。所以这个取舍的真正依据不是技术，是客户结构与交付物类型——把这句话说出来，比背结论更得分。

06无云端兜底下的降级阶梯

既然不能把任务甩给云，就必须明确「资源不够时逐级让什么」。每一级都要写进任务日志、可回溯、并在界面上给用户明确提示，绝不静默失败。

级别触发条件系统动作用户可见
L0显存余量充足正常并发排队正常进度
L1显存 > 18GB 或温度偏高分辨率 1024 → 768，保持步数提示「已自动降分辨率，可手动恢复」
L2批量积压 > 30 张候选数 4 → 2、步数 8 → 6队列页显示降级标记
L3需要切换精修模型卸载精修 / 只保留 Turbo，暂停后台批量明确告知切换耗时与排队位置
L4用户正在画布上编辑前台编辑优先，后台生成降为低优先级或暂停「已为您让出算力」提示
L5显存持续告警 / 磁盘将满拒绝新任务并说明原因与建议动作红色提示 + 一键清理缓存 / 稍后重试

07风险清单与许可审查

风险影响应对
模型许可不允许商用客户素材无法交付，法务风险只用 Apache 2.0 / 明确可商用的权重；上架前逐个核对 checkpoint、LoRA、放大器的许可
InsightFace / FaceID 系组件身份类 adapter 常附带非商用研究许可电商场景改用普通 IP-Adapter + 商品锚图 + LoRA，不用人脸方案
多模型同驻 OOM批量任务整批失败串行加载、用完卸载；显存预算预留 4GB
商品漂移（越生成越不像）一致性不可用每次 re-anchor 到原始商品图；固定 seed 只用于单变量调试
首图过慢被误认为卡死用户反复点生成，队列雪崩开机预热 + 明确的加载进度文案 + 重复提交拦截
中文文案渲染错字主图不能直接上架文字一律走后期排版叠加，或走 Qwen-Image 并人工校对
最容易写错的一句话不要在文档任何位置出现「性能不足时调用云端 API 兜底」。题目明确禁止，这一句会直接否定整份方案的端侧意识。

08老师可能追问什么（答辩准备）

「为什么不用最强的 FLUX.2？」
两个硬理由：社区许可非商用（电商/短剧都是要交货的），且 32B 模型 33.8GB 超出 24GB 显存，offload 后单张要几分钟，端侧批量不现实。
「没有云端兜底，慢了怎么办？」
答降级阶梯：降分辨率 → 减步数 → 卸载大模型 → 暂停后台保前台 → 明确拒绝并提示。绝不静默失败，也绝不偷调云 API。
「主观效果怎么算评估？」
答盲测 + 5 分制评分表 + 多人取均值 + 锚图 A/B + 固定 seed 可复现。主观维度也要可操作、可复议。
「并发不就是把任务排队吗？」
答四层：状态机、优先级与配额、按错误类型分类恢复、三层持久化（草稿 / 参数 / 产物）。排队只是第一层。
